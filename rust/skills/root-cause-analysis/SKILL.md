# 假设驱动的根因分析（Hypothesis-Driven Root Cause Analysis）

## 何时使用

任务属于以下任一时，先加载并遵循本 skill：
- "为什么 X 没有出现 / 失败 / 报错 / 不符合预期"
- 排查 bug、定位根因、解释一个观察到的异常现象
- 需要回答"原因是什么"，而不是"做什么"

## 核心原则

根因分析的收敛速度取决于**假设空间缩小的速度**，而不是**收集数据的数量**。
每多一个不服务于证伪假设的动作，就多浪费一次工具调用和 token。

## 五步流程

### 1. 问题定义
- 明确写出一句话：症状（观测到什么）、期望行为（应该怎样）、二者差异在哪。
- 尽量量化（时间点 / 数值 / 状态），不要停留在"好像不对"。

### 2. 生成候选假设（≥2 个）
- 列出 2+ 个可能的根因，按先验概率排序。
- 每个假设必须附带一个**可证伪预测**：若该假设为真，应观察到什么（可验证、且能区分其他假设）。

### 3. 设计最小验证
- 优先做**高区分度**的验证：一次动作能同时排除/确认多个假设。
- 典型高区分度动作：对照实验（正常 vs 异常）、diff（运行态 vs 回放态）、二分定位。
- 拒绝广搜：不读与当前假设无关的文件，不做"先看看再说"。

### 4. 执行 → 排除/确认 → 收敛
- 每个验证动作前，先写一句「这个动作要证伪哪个假设」。
- 验证后显式更新假设空间：哪个被排除、哪个概率上升。
- 假设空间应**单调缩小**；若某动作没让它缩小，说明该动作无效。

### 5. 无法收敛 → 澄清
- 若剩余假设无法用现有信息区分，或需要外部事实（用户环境 / 真实数据），
  立即向用户提出具体问题，而不是继续横向探索。

## 反模式（禁止）

- ❌ 一上来就认定某个假设，然后只找支持它的证据（确认偏误）
- ❌ 反复重写同一诊断脚本试错（v2/v3/…），而不是设计区分性验证
- ❌ 横向读大量无关文件/代码，却没有先明确要证伪什么
- ❌ 把"收集数据"当成"推进任务"——数据没让假设收敛就是原地打转

## 收尾

给出根因时，附上**证据链**：哪个假设被什么验证确认、哪些假设被排除。
若根因只是中间结论（如"被某门控跳过"），进一步说明该门控为何处于当前状态，
否则回答会停在表象。
