# 记忆闭环使用说明

这页只讲怎么观察和验收，不讲实现。涉及两个文件：

- `.claw/memory.json`：真正生效的记忆，模型每轮会看到它的投影。
- `.claw/memory_shadow.jsonl`：影子提议流水，只记录"当时如果生效会写下什么"，不参与召回。

## 1. 它在一轮里做了什么

一轮结束时，这一轮的对话被丢进一个后台队列（不阻塞回答）；后台攒够 8 轮或空闲 90 秒后，交给小模型判断"这一轮有没有值得长期记住的东西"，产出一条或多条记忆操作。之后按你选的三档模式处理：只记录、进影子投影、或真正落盘。

## 2. 三档模式

| 模式 | 会发生什么 | 会不会落盘 | 适用阶段 |
|---|---|---|---|
| `log-only`（默认） | 只把提议追加到 `memory_shadow.jsonl`，`/memory review` 可逐轮看 | 不会 | 首次启用、改完提取规则后 |
| `visible` | 提议进本会话的投影，模型能看到，但每条带 `[影子·未确认]` 标记 | 不会（重启即消失） | 验证"记忆被动用"是否合理 |
| `write` | 条目真正进记忆，跨会话保留 | 会（会话切换/退出时落盘） | 观察期通过后长期使用 |

切换方法（进程启动前设置，改完需重启会话才生效）：

```powershell
# PowerShell
$env:CLAW_MEMORY_MODE = "visible"
```

```bash
# bash / zsh
export CLAW_MEMORY_MODE=visible
```

不设或填了无法识别的值都会回退到 `log-only`，所以"忘了设"不会误写。

**建议顺序**：`log-only` 跑 1–2 天 → `visible` 跑 1 天 → `write`。

观察期各看什么：

- `log-only`：每天看一次 `/memory review`。重点不是"记得多不多"，而是误报——一次性指令、提问、临时代码状态有没有被写成记忆；同时记录"新增 / 去重 / 覆盖 / 拦截"的比例，拦截变多说明撤回机制在起作用。
- `visible`：正常干活，留意回答里有没有把 `[影子·未确认]` 的条目当成既定事实乱用。影子条目在投影里单独成段，不会混进已确认记忆。
- `write`：切换会话后看 `/memory list`，确认同一件事没有被写成两三条；隔天再确认改口后旧说法已经被覆盖，而不是新旧并存。

## 3. `/memory review` 怎么读

默认显示最近 20 条，`/memory review 50` 看最近 50 条。每条长这样：

```
  轮 sess-1a2b T12-T19  upsert
    目标      kind=UserProfile subject=user attribute=rust_indent
    内容      用户要求 Rust 改动统一用 4 空格缩进
    依据      basis=UserStated explicit=true confidence=High evidence=1
    判定      新增
```

逐行含义：

- `轮 … T12-T19`：这条提议来自哪几轮。`upsert` 表示新增或覆盖，`retract` 表示撤回。
- `目标`：记在哪个主体/属性下。`subject` 不在词表内的会被记为孤儿，等待你审阅（`/memory list` 里以 `!` 开头展示）。
- `basis`：这条记忆凭什么成立。
  - `UserStated`：用户第一人称讲的稳定属性（"我习惯…"）。一次就成立。
  - `Inferred`：从行为或失败模式推断出来的。要**出现两次**才成立，第一次只会留在候选池里。
  - `Constraint`：跨任务持续有效的环境、政策、依赖限制。一次就成立。
- `explicit`：用户是不是明确下了"记住/以后都/不要再"这类指令。它有一个实际作用：`explicit=true` 的条目即使 basis 是 `Inferred`，也跳过"二现"门槛，一次就成立。
- `confidence`：模型自评，`High/Medium/Low`。`Low` 的建议在 `write` 前优先人工确认。
- `判定`：此刻如果真写，会发生什么。
  - `新增`：没有冲突，会新建一条。
  - `去重（已存在：…）`：内容与现有条目一字不差，不会重复写。
  - `覆盖（与 N 条同 subject+attribute 条目冲突）`：同一主体属性下有旧条目，新值会顶掉旧的。
  - `拦截（subject 已撤回）`：你之前用 `/memory rm` 删过这个主体，系统按"墓碑"拦下，不会自动重抽。

看 review 的顺序建议：先扫"判定"，`拦截` 和 `覆盖` 多说明规则在收口；再扫"内容"，一次性指令出现在这里就是误报；最后看 `basis`，`Inferred` 占比过高说明模型在猜。

## 4. 其他子命令

| 命令 | 作用 | 什么时候用 |
|---|---|---|
| `/memory` 或 `/memory list` | 看记忆总览：各块容量、活跃条目、撤回集合、归档数、孤儿条目、影子条目、当前模式 | 每天扫一眼；模式切换后确认生效 |
| `/memory show <n>` | 看第 n 条的全部字段：内容、类别、来源、依据、置信度、出现次数、主体/属性、生效时间、最后验证时间 | 怀疑某条记错或过时时 |
| `/memory search <关键词>` | 在活跃条目的内容、来源、主体、属性里做包含匹配 | 想知道"某件事到底记没记" |
| `/memory rm <n>` | 软删除：条目迁入归档并留下墓碑，之后同一主体+属性不会再被自动重抽 | 记错了、过时了、涉密了 |
| `/memory undo` | 撤销最近一次撤回：移除墓碑，允许重新写入 | 删错了立刻恢复 |

`rm` 的编号是活跃条目的 `#1…N`；影子条目排在它们之后，用大于 N 的编号删除（`/memory list` 里影子条目标为 `s1、s2…`，删除时按活跃条目数往后数）。删除影子条目只影响当前会话投影，因为它本来就没落盘。

## 5. 影子条目在投影里长什么样

`visible` 模式下，注入给模型的记忆片段会多出一段：

```
## Human
- 用户偏好 Rust 4 空格缩进

## Shadow (unconfirmed)
- [影子·未确认] 用户正在把回测周期从 5 分钟改成 15 分钟
```

要点：

- 影子条目**只存在于当前进程的内存投影**，不写 `memory.json`，重启后自然消失。
- 每条都必须带 `[影子·未确认]`，不会伪装成已确认记忆。
- 觉得不合适，当场 `/memory rm <编号>` 撤销；不必等它落盘。

## 6. 切到 write 之前的四个自检动作

按顺序做一遍，每个动作看 `/memory review` 的最新一条。四项都合格再切 `write`。

| 动作 | 怎么说 | 期望看到 | 什么算不合格 |
|---|---|---|---|
| 一个明确偏好 | "以后 Rust 改动统一用 4 空格缩进，不要 tab。" | `basis=UserStated`、`explicit=true`、判定 `新增` | 没出现；或 basis 被写成 `Inferred`；或内容被改写走样 |
| 一个隐含偏好（不说"记住"） | 连续两轮都提到"我习惯先看日志再看代码" | 第一次最多进候选池，不产生条目；第二次判 `新增` | 第一次就落库（门槛失效）；或两次都不出（漏报） |
| 改口一次 | "刚才说 4 空格，改成 2 空格。" | 判定 `覆盖`（或先 `撤回` 再 `新增`），`/memory list` 里只剩 2 空格这条有效 | 新旧两条并存；或旧条被删但新条没进 |
| 一句临时指令 | "这次只改这一个文件，别的别动。" | 不产生条目，或出现但被判 `拦截` | 被写成长期约束并进入 `write` |

补充两个检查：

- 说一句"请你分析一下为什么没触发信号"：这是请求排查，不是纠正，**不应该**入库。入库了说明识别口径过宽。
- 说一句"前端还是再画线段，这和定义不符"：这是纠正，**应该**入库，且 basis 为 `UserStated`。

## 7. 已知边界

- **一次性指令仍可能误报**：改后的规则已经点名排除"这次不要…/这一步必须…/期间我不在电脑前…"这类说法，但实测 96 次里仍有 3 次把长段落指令写进来（其中 1 次改前就有）。看到这类条目，直接 `/memory rm`，不用改配置。
- **"请你分析一下"这类请求核查不会入库**：correction 只认"实现与定义不符 / 追问式否定 / 新证据推翻旧结论"三种断言；"我记得好像…你检查一下"属于模糊记忆核查，宁可漏也不写。这是有意的保守，不是故障。
- **强杀进程最多丢一个窗口**：还没攒够 8 轮、也没到 90 秒的证据会随进程消失；正常退出、`/resume`、`/clear` 都会先冲刷。所以别用任务管理器结束进程来"省时间"，最多损失最近几轮。
- **单次结果不代表水平**：同一份内容跑两次，召回会有几个点的自然波动；判断规则改动是否有效，至少看 5–6 次、并且改前改后交错跑。
