# 助手重复诊断死循环 —— 3 个机制缺陷修复记录

> 现象：助手会一直重复同一组诊断动作（如反复运行 `bash 诊断 → 报错 → 换参数再诊断`），导致会话卡死。
>
> 结论：这不是模型行为问题，而是 **3 个代码机制缺陷** 共同导致的，本次已全部修复并通过验证。

---

## 一、修复的 3 个 BUG

| # | 文件 | BUG | 根因 |
|---|------|-----|------|
| 1 | `history_search.rs` | **跨会话中文检索失效**（最核心） | SQLite FTS5 的 `unicode61` tokenizer 对连续 CJK 文本**不切词**——`继续帮我配置飞书` 被当成 1 个 token，2 字查询 `飞书` 永远无法命中 → 助手 `session_search` 搜不到历史，被迫"从零重建上下文"→ 反复诊断 |
| 2 | `loop_detection.rs` | **循环检测只覆盖文件编辑** | 原实现只跟踪 `file_edited` 事件（同文件 5 次警告 / 10 次中止），`bash 诊断→报错→换参数再诊断` 这类**工具调用循环**完全没有防护 |
| 3 | `conversation.rs` | **主对话无迭代上限** | 默认 `max_iterations: usize::MAX`——一旦助手陷入循环，turn 内可以无限自转，卡死会话就是这么产生的 |

### 修复要点

- **Bug-1（中文检索）**：索引端与查询端双向处理——索引时连续汉字间插入空格使 FTS5 按单字建 token；查询时 CJK 拆字为 `字1 AND 字2 ...`，ASCII 与 FTS5 运算符原样透传；旧库检测到 v1 表（无 `history_meta`）时在事务内自动迁移重建。
- **Bug-2（循环检测）**：在文件编辑通道之外新增 `record_tool_call` 通道，跟踪工具调用模式，不破坏原有 5/10 阈值行为。
- **Bug-3（迭代上限）**：主对话引入迭代上限，subagent（32）保持兼容，防止 turn 内无限自转。

## 二、写代码过程中遇到的真实障碍

> 说明：以下按代码注释 / 测试中留下痕迹的确认事实记录。

### 1. FTS5 语法陷阱 —— 括号表达式后接 token 是语法错误 ⭐ 最折磨人的一个

- 查询拆字后会产生 `(飞 AND 书) 继续` 这类串，SQLite 直接报语法错误
- 代码里专门留了两处注释记录这个坑（`history_search.rs` L237、L297）：括号表达式后跟普通词**必须显式补 `AND`**
- 这个问题是反复跑测试试出来的——第一次测试在 `query("飞书 配置")` 这种混合查询上炸掉

### 2. 中英文混合查询的兼容处理

- 拆字逻辑不能碰英文 / 短语 / 布尔运算符（`"rust toolchain"`、`OR`、`NOT` 必须原样透传）
- 写 tokenizer 时很容易误伤 ASCII——最终用"连续汉字串"判定 + 白名单字符集解决

### 3. v1→v2 表迁移的安全设计

- 旧库的 FTS5 表（`history`）和新结构（多了 `history_meta`）要能自动识别
- 迁移必须**事务内**完成（读全部行 → DROP → 重建 → CJK 切分重插），中途断电不能损坏原库
- 验证迁移时**先用真实库副本测试**（`history.db.bak-20260809-012643`），确认没问题才敢让正式代码自动迁移

### 4. FTS5 rank 方向坑

- FTS5 的 BM25 `rank` 是**越负越相关**，写加权排序（decision ×0.5）时方向极易搞反——这个坑在代码注释 L118 里明确记录了

### 5. loop_detection 双通道合并

- 原有 Hook 结构只处理文件编辑事件，要新增 `record_tool_call` 通道且**不能破坏原有 5/10 阈值行为**——改类型定义时编译器会抓出所有调用点，这个相对顺利

## 五、第二轮加固（根本性修复，2026-08-09）

> 第一轮修复了 3 个机制缺陷的**症状**;第二轮解决**根因**:助手丢失"已尝试且失败"状态、
> 循环检测无执行权且跨 turn 失效、终止路径无诊断。实施计划见 `docs/plans/2026-08-09-loop-prevention.md`。

### 5.1 第一轮修复的 4 个残留缺陷

| 残留缺陷 | 位置 | 后果 |
|---------|------|------|
| 检索结果被 CJK 切分空格污染 | `history_search.rs` content 列 | 助手"回忆历史"读到的内容是 `继 续 帮 我 配 置 飞 书 ` |
| `<attempted>` 记账依赖 LLM 主动调用 | `notebook_update` | 循环中的 LLM 不会停下来记账 → 已尝试状态永远缺失 |
| 循环检测每 turn 全量 reset + Abort 仅标错 | `conversation.rs` 每 turn reset + `run_post_tool_use_hook` | 跨 turn 循环不可见;Abort 后 turn 继续 |
| 失败路径完全绕过循环检测 | `run_post_tool_use_failure_hook` | "命令报错 → 换参数再报错"循环无法捕获 |

### 5.2 本轮改动

- **P0-检索**：history FTS5 增加 `content_raw UNINDEXED` 列存原文，`search` 返回原文；v1/v2 → v3 自动迁移（v2 用逆变换还原切分文本）。
- **P0-预防**：失败工具调用由运行时自动记入 NOTEBOOK `<attempted>` 段（去重 + 容量裁剪），不依赖 LLM 主动调用。
- **P1-检测**：LoopDetector 工具调用计数按 15 分钟窗口跨 turn 衰减；输出规范化（剥离时间戳/折叠空白）；失败路径同样接入检测。
- **P1-执行**：Loop Abort 真正终止 turn（`loop_abort_reason` + 工具循环终止点），不再只把工具结果标错。
- **P2-兜底**：迭代上限与 abort 错误消息携带 `<attempted>` 段诊断指引。
